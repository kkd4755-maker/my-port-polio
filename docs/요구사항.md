## 1. 목적과 대상

### 1.1 목적

개인 브랜딩. 이름을 검색했을 때 가장 먼저 나오는, 나를 대표하는 한 페이지를 만든다.
채용 지원용 이력서가 아니라 **"이 사람이 무엇을 해왔고 무슨 생각을 하는 사람인가"** 를 보여주는 홈이다.

### 1.2 주 독자

| 독자 | 방문 맥락 | 이 사람이 얻어가야 할 것 |
|---|---|---|
| 기술 커뮤니티 / 동료 개발자 | 발표·글·SNS에서 링크를 타고 유입 | 이 사람이 어떤 분야에 있고 어떤 글을 쓰는지 |
| 협업·제안 문의자 | 소개를 받고 확인차 방문 | 신뢰할 만한 이력과 연락 수단 |
| 채용 담당자 (부차적) | 이름 검색 | 경력 흐름의 큰 그림 |

### 1.3 성공 기준

- 첫 화면 진입 후 **5초 안에** "누구이고 무엇을 하는 사람인지" 파악 가능
- 모바일에서 세로 스크롤만으로 전체 내용 소비 가능
- Lighthouse 기준: Performance ≥ 95, Accessibility = 100, Best Practices ≥ 95, SEO ≥ 95
- 초기 로드 JS ≤ 30KB (gzip 기준), 폰트 포함 총 전송량 ≤ 300KB — React 전환으로 JS가 gzip 약 75KB가 되어 **현재 미달**이다 (§8.5)

### 1.4 명시적 비목표 (Non-goals)

- 백엔드 / 데이터베이스 / 로그인 없음. 순수 정적 사이트다.
- CMS 연동 없음. 콘텐츠는 저장소 안의 데이터 파일로 관리한다.
- 댓글, 방명록, 조회수 카운터 없음.
- **다국어(i18n) 없음.** 한국어 단일. 이름·직함·태그라인만 영문 병기한다.
- **이력서 PDF 다운로드 없음.** 개인 브랜딩 목적에서 우선순위가 낮다.
- **Experience 필터 없음.** 항목 수가 10개 미만이면 과한 기능이다.
- **분석 도구 없음.** 외부 요청 0개 원칙을 지킨다.
- **Skills 섹션 없음.** 기술 스택 나열은 이력서형 구성이며 이 사이트의 목적과 다르다. (Projects는 v1.3에서 예외로 추가했다. §3.7, §8.6 참고)

## 2. 기술 스택과 제약

### 2.1 확정 스택

- **React + TypeScript + Vite** (v1.2에서 바닐라 TS에서 전환, §8.5). `@vitejs/plugin-react` 사용.
- 스타일은 **순수 CSS + CSS 커스텀 프로퍼티**. Tailwind 등 도입 안 함.
- 런타임 의존성은 `react`, `react-dom`만 허용한다. 개발 의존성은 `vite`, `typescript`, `@vitejs/plugin-react`, `@types/react`, `@types/react-dom`.

v0.1~v1.1에서는 페이지가 1개이고 상태 변화가 테마 토글과 스크롤 관찰 정도라 프레임워크를 쓰지 않기로 했다. v1.2에서 이 결정을 뒤집어 React로 전환했다. 그 대가로 번들 크기 목표(§1.3)를 잃었다. 근거와 남은 과제는 §8.5에 있다.

### 2.2 기존 규약 준수 (CLAUDE.md)

- 로컬 import는 `.ts` 확장자 명시 (`./theme.ts`)
- 타입 전용 import는 `import type`
- enum / namespace / 생성자 매개변수 프로퍼티 사용 불가 (`erasableSyntaxOnly`)
- 사용하지 않는 지역 변수·매개변수는 빌드 실패를 유발함
- `public/` 에셋은 절대 경로, `src/assets/` 에셋은 import

### 2.3 렌더링 구조 (확정)

초기 스타터는 `main.ts`가 `#app.innerHTML`에 템플릿 문자열을 통째로 대입하는 구조였다. 섹션이 5개로 늘어나면 비대해지므로 아래 구조로 분리했고, v1.2에서 헤더를 React 컴포넌트로 옮겼다.

```
vite.config.ts         # 메타 태그 / robots / sitemap 을 profile.ts 에서 생성
src/
  main.tsx             # React 마운트(flushSync) + 테마·스크롤 DOM 연결
  App.tsx              # React 컴포넌트와 문자열 섹션을 순서대로 조립
  components/          # React 컴포넌트 (파일 하나에 컴포넌트 하나)
    Header.tsx         # 로고 + 네비게이션 + 테마 토글 버튼
    About.tsx          # 소개 (문단은 data/profile.ts)
    Projects.tsx       # 작업물 (데이터 배열이 파일 상단에 있음)
    Contact.tsx        # 이메일 + 소셜 링크 (데이터는 data/profile.ts)
  data/                # 콘텐츠 (내용 수정은 여기만 건드림)
    profile.ts         # 이름, 태그라인, 소개문, 소셜 링크, 사이트 메타
    experience.ts      # 타임라인 항목 배열
    posts.ts           # 글 목록 배열
  sections/            # 각 섹션의 HTML 문자열을 반환하는 순수 함수
    header.ts          # 미사용 (Header.tsx로 대체)
    hero.ts
    about.ts           # 미사용 (About.tsx로 대체)
    experience.ts
    writing.ts
    contact.ts         # footer()만 사용 (Contact 섹션은 Contact.tsx로 대체)
  lib/
    theme.ts           # 다크/라이트 토글
    reveal.ts          # IntersectionObserver 스크롤 애니메이션 + 네비 활성 표시 + 헤더 보더
    html.ts            # 태그드 템플릿 + HTML 이스케이프
  App.css
```

핵심 원칙: **콘텐츠(data)와 표현(sections)을 분리한다.** 경력 한 줄을 추가할 때 HTML을 건드리지 않아야 한다.

`lib/html.ts`의 이스케이프 유틸은 `innerHTML`에 데이터를 넣기 때문에 필요하다. 지금은 내가 쓴 데이터만 들어가지만, 규약으로 세워두면 나중에 외부 데이터를 넣을 때 사고를 막는다.

## 3. 화면 구성

전체는 **단일 페이지 세로 스크롤**. 상단에 고정 네비게이션을 두고 앵커로 이동한다.
섹션 순서: Hero → About → Experience → Projects → Writing → Contact. (Projects는 v1.3에서 추가, §3.7)

### 3.1 공통 — 헤더 / 네비게이션

- 좌측: 이름 로고타입 (클릭 시 최상단)
- 우측: 섹션 앵커 링크 + 테마 토글 버튼
- 스크롤 시 배경에 블러 + 미세한 하단 보더 (`position: sticky`)
- 현재 보고 있는 섹션의 앵커에 활성 표시 (IntersectionObserver 재사용)
- **모바일(~639px): 햄버거 메뉴를 만들지 않는다.** 앵커 링크를 숨기고 로고와 테마 토글만 남기며, 내용은 스크롤로 소비한다. 섹션이 5개뿐이라 메뉴를 여닫는 비용이 스크롤보다 크다.

### 3.2 Hero

첫 화면. 스크롤 없이 보이는 영역에서 아래를 전달한다.

- 프로필 이미지 — 원형, 소형(96~120px). 실물 사진이 준비될 때까지는 이니셜 아바타를 두고, `data/profile.ts`의 경로만 교체하면 되게 한다.
- 이름 (한글 + 영문 병기)
- 한 줄 태그라인 — 직함이 아니라 **하는 일에 대한 문장**으로. (예: "쓰는 것으로 생각을 정리하는 프론트엔드 개발자")
- 보조 문장 1~2줄
- CTA: `글 읽기` (Writing 앵커) / `연락하기` (Contact 앵커)
- 소셜 링크 아이콘 행 (GitHub, 블로그, 이메일 등)

미니멀 타이포 방향에 맞춰 Hero는 큰 배경 이미지나 그라디언트 없이 **여백과 폰트 크기 대비**로만 구성한다.

### 3.3 About

- 3~5문단 분량의 자기소개 산문. 불릿 나열이 아니라 읽히는 글로.
- 관심 분야 / 지향점 / 일하는 방식

### 3.4 Experience / Timeline

세로 타임라인. 최신 항목이 위로 온다.

각 항목의 데이터 구조:

```ts
type ExperienceItem = {
  period: string;        // "2023.03 – 현재"
  title: string;         // 직함 또는 활동명
  org: string;           // 회사 / 기관 / 커뮤니티
  orgUrl?: string;
  summary: string;       // 한 줄 요약
  highlights: string[];  // 성과·담당 항목 2~4개
  tags: string[];        // 사용 기술 / 키워드
};
```

경력, 교육, 커뮤니티 활동을 **하나의 타임라인에 통합**하되 태그로 구분한다. 개인 브랜딩 성격상 발표·기고·오픈소스 기여도 경력과 동등한 무게로 다룬다. 필터 UI는 넣지 않는다.

### 3.5 Writing

이 사이트의 알맹이다. Hero와 About이 "누구인가"를 말한다면, 이 섹션이 "무슨 생각을 하는가"를 증명한다.

- 대표 글 3~6개를 목록으로
- 각 항목: 제목, 발행일, 한 줄 요약, 게재 매체, 외부 링크
- **관리 방식: 외부 블로그(velog / Medium / 티스토리 등)의 글을 `data/posts.ts`에 수동 등록한다.** 글쓰기 경험은 기존 플랫폼 그대로 쓰고, 여기서는 대표작만 큐레이션한다.

```ts
type Post = {
  title: string;
  date: string;      // "2026-03-14"
  summary: string;
  platform: string;  // "velog"
  url: string;
};
```

- 외부 링크는 `target="_blank" rel="noopener noreferrer"`, 새 창으로 열림을 스크린리더에 알린다.
- 목록 하단에 "전체 글 보기" 링크로 외부 블로그 홈으로 보낸다.

### 3.6 Contact / Footer

- 이메일 — 평범한 `mailto:` 링크로 간다. 스팸 봇 대비 난독화보다 접근성과 편의가 우선이다.
- 소셜 링크
- 저작권 표기, 마지막 업데이트 일자

### 3.7 Projects (v1.3 추가)

작업물 목록. §1.4의 원래 비목표를 사용자 결정으로 뒤집어 추가했다 (§8.6).

```ts
type Project = {
  title: string;
  summary: string;   // 한 줄 요약
  tags: string[];    // 사용 기술 / 키워드
  url?: string;      // 없으면 제목만 표시
};
```

- 데이터는 `components/Projects.tsx` 파일 상단의 `projects` 배열에 둔다. 항목을 추가하려면 배열 끝에 객체 하나만 더하면 된다. (`data/` 분리 원칙의 예외)
- 마크업과 스타일은 Writing의 `post-list` / `post`, `tag-list` / `tag` 클래스를 재사용한다. 전용 CSS는 없다.
- 현재 3개 항목은 플레이스홀더다.

### 3.8 디자인 원칙 (v1.4 추가)

지금까지 디자인 요구사항은 "미니멀 타이포" 한 줄뿐이었다. 사용자와 논의해 아래 방향을 확정한다. 결정 배경은 §6 #11.

**콘셉트: 에디토리얼 본문 + 랜딩식 첫 화면.** 읽는 구간(About·Writing)은 잡지·에세이의 리듬으로, 첫 화면과 구획은 제품 랜딩페이지의 정돈된 임팩트로 만든다.

| 항목 | 결정 |
|---|---|
| 분위기 | 에디토리얼. 넓은 여백, 세리프 제목, 읽기 좋은 행간 |
| 색 | 거의 흑백 + **포인트 1색(테라코타)**. 포인트는 CTA·링크·네비 활성 표시에만 쓴다. 나머지는 전부 명암 |
| 제목 서체 | 세리프. 본문은 시스템 산세리프 유지 |
| 프로필 사진 | 원형 96~120px, 태그라인 위. 타이포가 주인공 |
| 구조 | 섹션은 카드나 가로선·번호 없이 **여백과 2열 배치**로 구분한다. 데스크톱(1024px~)은 제목(왼쪽, 스크롤 따라옴) + 본문(오른쪽), 모바일은 제목 위 본문 아래 1단 |
| Projects | 카드 그리드로 Writing의 목록과 시각적으로 구분한다. 현재 구현은 모바일 가로 스크롤 카드, 태블릿 이상 자동 열(3개면 3열). 호버 시 미세한 상승과 포인트 색 보더 |

**Hero 구성:** 태그라인을 세리프로 크게 세운다(`--text-hero`, `clamp(2.25rem, …, 4rem)`). 이름(h1)은 그 위의 작은 눈썹 라인으로 내렸다. 읽기 폭(48rem) 안에서 한글 24자가 3줄 이내로 들어가는 크기가 4rem이라 그 이상은 키우지 않았다. 그 아래 보조 문장, CTA 2개(`글 읽기`는 포인트 색 채움 버튼, `연락하기`는 외곽선 버튼), 소셜 아이콘 행 순서다. §1.3의 "5초 안에 파악" 기준은 이 Hero가 충족해야 한다.

**색 규칙:**
- 배경·텍스트·보더는 무채색 계열(따뜻한 오프화이트 유지). 포인트 색만 채도를 가진다.
- **확정 값:** 라이트 `--accent: #a8481f`(배경 위 5.6:1, 흰 글자 버튼 5.8:1, `--accent-wash` 위 5.1:1), 다크 `#ee9a76`(배경 위 8.7:1). 처음 후보였던 `#b4532a`는 wash 위에서 4.4:1로 AA에 못 미쳐 탈락했다.
- 하드코딩 색 금지 원칙은 그대로다. 포인트 색도 `--accent` 토큰 값만 바꾼다.

**타이포 규칙:**
- 작은 고정폭(mono) 글자는 쓰지 않는다. 기간·태그·푸터 모두 본문 서체를 쓴다. 명세서 같은 인상을 준다.
- 소개의 첫 문단은 크고 진한 리드 문장으로, 나머지는 차분하게 둔다.
- 세리프는 h1~h3와 섹션 번호 라벨에만 쓴다. 본문·UI·태그는 산세리프.
- 본문 읽기 폭은 약 65자(`max-width: 40rem` 안팎), 행간 1.7 이상. 전체 컨테이너는 62rem이고 본문은 오른쪽 열 안에서 이 폭을 지킨다.

**모션:** §4.2의 페이드인을 그대로 쓴다. 랜딩 느낌을 위해 카드 호버 시 미세한 상승·보더 색 전환 정도만 더하고, 화려한 효과는 넣지 않는다. `prefers-reduced-motion`에서는 모두 끈다.

**세리프 서체 방침 (확정):**
- **Noto Serif KR**(OFL 라이선스)을 **제목에 실제로 쓰는 글자만 뽑은 서브셋**으로 셀프 호스팅한다. 굵기는 1개(제목용 SemiBold 또는 Bold)로 시작한다.
- 파일은 `public/fonts/`에 woff2로 두고 `App.css`에 `@font-face`(`font-display: swap`)를, `index.html`에 `<link rel="preload">`를 추가한다. 폴백은 시스템 세리프다(`'Noto Serif KR 서브셋', 'AppleMyungjo', Batang, Georgia, serif` 순서). 서브셋에 없는 글자는 폴백으로 표시된다.
- **실측 (2026-09-20, SemiBold 600, 현재 플레이스홀더 기준):** 한글 106자 포함 **29.9KB**. 한글 글자 수에 대략 비례해 늘어난다(약 0.11KB/자): 200자 약 40KB, 400자 약 65KB, 800자 약 113KB, KS X 1001 전체 2,350자 약 291KB. 실물 콘텐츠 제목이 한글 400자 안팎이면 예산(300KB)의 4분의 1 이하다. 전체 서브셋(B안)은 예산을 거의 다 쓴다는 점이 실측으로 확인됐다.
- 생성 스크립트: `scripts/subset-serif.py`, 결과물: `public/fonts/noto-serif-kr-heading.woff2`. 아직 CSS·`index.html`에서 참조하지 않는다.
- **갱신은 수동 스크립트로 한다.** 제목·라벨 문자열을 `src/data/`에서 모아 서브셋을 다시 만드는 명령을 `scripts/`에 두고, 콘텐츠를 바꾼 뒤 직접 실행한다. 빌드에는 Python 등 외부 도구 의존을 넣지 않는다.
- 탈락: 시스템 세리프(OS별 한글 모양 불일치), 전체 서브셋(예산 소모), 영문·숫자만 세리프(에디토리얼 인상 약화).

**미결정 (구현 전에 정할 것):**
- ~~세리프 서체 선택~~ → 확정, 아래 "세리프 서체 방침" 참고.
- (해결, 번복) 섹션 번호는 처음에 본문 제목에 붙이기로 했으나 **제거했다.** 섹션은 순서가 있는 단계가 아니라서 번호가 문서 목차처럼 읽혀 "보고서 초안" 느낌을 만들었다. 가로선도 같은 이유로 제거했다.

## 4. 기능 요구사항

### 4.1 다크 / 라이트 테마 토글

- CSS 커스텀 프로퍼티로 색을 토큰화한다. `:root`에 라이트, `[data-theme="dark"]`에 다크를 정의.
- 최초 방문: `prefers-color-scheme` 시스템 설정을 따른다.
- 사용자가 토글하면 `localStorage`에 저장하고 이후 그 선택을 우선한다.
- **FOUC 방지**: `index.html`의 `<head>`에 인라인 스크립트로 저장된 테마를 `<html>`에 먼저 적용한다. 번들 로드를 기다리면 흰 화면이 번쩍인다.
- `localStorage` 접근은 `try/catch`로 감싼다. 프라이빗 모드에서 예외가 날 수 있다.
- 토글 버튼은 `aria-pressed`로 상태를 노출한다.

### 4.2 스크롤 애니메이션

- `IntersectionObserver`로 섹션·카드 진입 감지 → `.is-visible` 클래스 부여 → CSS `transition`으로 페이드인 + 소폭 상승(16~24px).
- 한 번 나타난 요소는 다시 숨기지 않는다 (`unobserve`).
- **`prefers-reduced-motion: reduce`일 때 모든 이동·페이드를 끄고 즉시 표시한다.** 접근성 필수 항목.
- JS가 실패해도 콘텐츠는 보여야 한다. `lib/reveal.ts`가 옵저버 설정에 성공한 뒤 `<html>`에 `reveal-ready`를 붙이고, CSS는 그 클래스 아래에서만 초기 숨김을 건다. 번들 로드 실패나 `IntersectionObserver` 미지원이면 클래스가 안 붙으므로 콘텐츠는 그냥 보인다.

### 4.3 반응형

| 브레이크포인트 | 대상 | 레이아웃 |
|---|---|---|
| ~ 639px | 모바일 | 1단, 좌우 패딩 16px, 네비 앵커 숨김 |
| 640 ~ 1023px | 태블릿 | 1단, 좌우 패딩 32px, 폰트 상향 |
| 1024px ~ | 데스크톱 | 본문 최대 폭 720~800px 중앙 정렬 |

- **모바일 우선**으로 작성한다 (기본 스타일 = 모바일, `min-width` 미디어 쿼리로 확장).
- 타이포 스케일은 `clamp()`로 유동 처리해 브레이크포인트 개수를 줄인다.
- 가로 스크롤은 어떤 폭에서도 발생하지 않아야 한다.

### 4.4 접근성 (필수 기준)

- 시맨틱 HTML: `header` / `nav` / `main` / `section` / `article` / `footer`, 제목 레벨은 h1 → h2 → h3 순서를 건너뛰지 않음
- 페이지당 `h1`은 1개 (Hero의 이름)
- 모든 이미지에 의미 있는 `alt`, 장식용은 `alt=""`
- 키보드만으로 모든 인터랙션 가능, 포커스 링을 제거하지 않음 (`:focus-visible` 사용)
- "본문 바로가기" 스킵 링크
- 명도 대비 WCAG AA (본문 4.5:1, 큰 텍스트 3:1) — **라이트/다크 양쪽에서** 검증
- 각 섹션에 `aria-labelledby`로 제목 연결
- 아이콘 전용 버튼에 `aria-label`
- `scroll-behavior: smooth`도 `prefers-reduced-motion`에서 해제

### 4.5 SEO / 메타

- `<title>`, `meta description`, `canonical`
- Open Graph + Twitter Card (OG 이미지 1200×630)
- `application/ld+json`으로 `Person` 스키마 — 개인 브랜딩 목적상 이름·직함·소셜 프로필(`sameAs`)을 정확히 채운다
- `sitemap.xml`, `robots.txt`
- `lang="ko"`

### 4.6 성능

- 폰트는 **시스템 폰트 스택**을 쓴다 (Pretendard가 로컬에 설치돼 있으면 사용, 없으면 OS 기본 한글 서체). 전송량 0, 외부 요청 0, FOIT/FOUT 없음. 웹폰트를 꼭 써야 한다면 셀프 호스팅 + `font-display: swap` + `preload` + 한글 서브셋으로 추가한다 — §8 참고.
- 이미지는 WebP/AVIF, `width`/`height` 명시로 CLS 방지, 뷰포트 밖은 `loading="lazy"`
- **외부 요청 0개.** 분석 도구도 폰트 CDN도 쓰지 않는다.

### 4.7 배포

- **Vercel.** Git 연동 푸시 자동 배포, 빌드 설정 무설정(`vite build` / `dist` 자동 인식), `vite.config.ts`의 `base` 조정이 필요 없다.
- 커스텀 도메인은 나중에 연결한다. 도메인 없이도 `*.vercel.app`로 공개 가능하다.
- 저장소는 아직 git으로 초기화되어 있지 않다. 배포 단계에서 `git init` → GitHub 원격 연결이 선행되어야 한다.

## 8. 구현 메모

### 8.1 요구사항과 달라진 점

| 항목 | 요구사항 | 구현 | 이유 |
|---|---|---|---|
| 폰트 | 셀프 호스팅 웹폰트 | 시스템 폰트 스택 | 웹폰트 파일이 없고, 시스템 스택이 "외부 요청 0개"와 전송량 목표에 더 잘 맞는다. 브랜드 서체가 필요하면 §8.2 참고. |

| 메타 태그 | `index.html`에 직접 | `vite.config.ts` 플러그인이 주입 | `profile.ts` 하나를 단일 출처로 두기 위해서다. 빌드 결과는 정적 HTML이라 JS를 실행하지 않는 OG 크롤러도 읽는다. `robots.txt` / `sitemap.xml`도 같은 방식으로 생성된다. |

### 8.2 웹폰트를 추가하려면

Pretendard 같은 서체를 쓰려면 폰트 파일을 `public/fonts/`에 두고 `App.css`에 `@font-face`를, `index.html`에 `<link rel="preload">`를 추가하면 된다. 한글 서브셋(필요한 글자만 남긴 woff2)으로 줄이지 않으면 파일 하나가 1MB를 넘어 총 전송량 300KB 목표를 깬다.

### 8.3 OG 이미지 갱신

원본은 `docs/og-source.svg`이고 결과물은 `public/og.png` (1200×630)다. 원본을 고친 뒤에는 PNG를 다시 만들어야 한다. 별도 도구 없이 Chrome으로 변환할 수 있다.

```sh
chrome --headless --disable-gpu --window-size=1200,630 \
  --screenshot=public/og.png docs/og-source.svg
```

### 8.4 배포 전 반드시 바꿔야 하는 값

- `src/data/profile.ts`의 `siteUrl` — 현재 `https://example.com`. canonical / OG / sitemap / robots 가 전부 이 값을 쓴다.
- `src/data/profile.ts`, `experience.ts`, `posts.ts`의 플레이스홀더 콘텐츠 전부.
- `public/avatar.svg` — 이니셜 아바타. 실물 사진으로 교체.
- `docs/og-source.svg`의 이름·태그라인, 그리고 재생성한 `public/og.png`.
- 제목용 세리프 서브셋(`public/fonts/`) — 콘텐츠를 실물로 바꾼 뒤 서브셋 스크립트를 다시 실행한다. 빠뜨리면 일부 제목 글자만 폴백 서체로 보인다.

### 8.5 React 전환 (v1.2)

헤더를 React 컴포넌트로 만들기 위해 바닐라 TS 구조에서 React로 전환했다. 요구사항 §2.1의 "프레임워크 도입 안 함" 결정을 의도적으로 뒤집은 것이다.

- **변경:** `main.ts` → `main.tsx`, `App.tsx`와 `components/Header.tsx` 추가, `vite.config.ts`에 `@vitejs/plugin-react`, `tsconfig.json`에 `"jsx": "react-jsx"`.
- **과도기 구조:** Header, About, Projects, Contact는 React 컴포넌트이고, Hero·Experience·Writing·footer는 `sections/`의 문자열 템플릿을 `dangerouslySetInnerHTML`로 삽입한다. React 자식과 `dangerouslySetInnerHTML`은 한 요소에 함께 쓸 수 없어, 문자열 섹션은 `<div>`로 감싸 컴포넌트 사이에 끼운다. 나머지도 React로 옮길지는 미정이다.
- **`main.tsx`의 동기 렌더:** `flushSync`로 렌더한 직후 `setupThemeToggle` / `setupReveal` 등을 실행한다. 비동기 렌더로 바꾸면 `reveal-ready` 설정이 첫 페인트 뒤로 밀려 초기 숨김이 깜빡인다.
- **미사용 파일:** `sections/header.ts`, `sections/about.ts`는 React 컴포넌트로 대체되어 남아 있다. 지워도 된다. `sections/contact.ts`는 `footer()` 때문에 지우면 안 된다.
- **번들 크기:** JS가 gzip 약 75KB로 늘어 §1.3의 30KB 목표를 넘는다. 목표를 완화하거나 Preact 호환 레이어(`preact/compat`)로 줄이는 방안이 있다.

### 8.6 Projects 섹션 추가 (v1.3)

§1.4와 결정 #10은 Projects를 이력서형 구성이라며 제외했다. 사용자 요청으로 이 결정을 뒤집어 추가했다.

- **위치:** Experience와 Writing 사이. 섹션 id는 `projects`.
- **네비게이션:** `data/profile.ts`의 `navItems`에 항목을 추가하지 않았으므로 상단 메뉴 링크와 스크롤 활성 표시가 없다. 필요하면 `navItems`에 `{ id: 'projects', label: '작업물' }`을 추가한다.
- **콘텐츠:** 3개 모두 플레이스홀더다. 9단계에서 실물로 교체한다. URL도 예시 주소다.
